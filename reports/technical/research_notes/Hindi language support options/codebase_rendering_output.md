# Codebase audit: where rendering, on-screen text, fonts, publishing and the UI assume English / Latin script

Scope: read-only audit of the Visio Studio repository on 18 Nov 2026 (no repository file was changed apart from this notes file). Citations are `path:line` relative to the repository root. Besides reading code, a few throwaway experiments were run inside the locally built Docker images (`visio-studio-backend`, `visio-studio-motion`, both built 17 Nov 2026) with `docker run --rm`; their outputs went to `/tmp/visio_audit/` (outside the repository). They are cited as "Experiment E1…E7" and described where first used. A macOS system font (Kohinoor Devanagari, copied to `/tmp`) was used as a stand-in Devanagari font for the experiments only; it is not a recommendation for the product.

Size legend used throughout: **S** = under a day (constants, one file, a flag); **M** = 1 to 3 days (several files and/or both renderers, plus re-tuning and visual checks); **L** = more than 3 days or depends on a new model/capability. Architecture legend: **All** = needed under A (native Hindi), B (English pivot, translate in/out) and C (hybrid: English reasoning, Hindi speech/display), because all three put Hindi speech and Hindi text on screen; otherwise the architectures are named.

There is no project-level language setting today. The only "language" field in the data is the Story Bible's, which code always writes as `en` (`backend/app/services/story_bible_writer.py:11-12`, `:30`, `:216`; `backend/app/services/story_bible.py:173`) and which no downstream writer reads (`graphic_theme_writer.bible_for_model` passes only title, genre, tone, visual style and narration, `backend/app/services/graphic_theme_writer.py:98-107`). The design doc states "The system works in English only, so every story, narration line and dialogue line is in English" (`Path_ahead.md:326`).

## 1. Captions (caption_plan.py, caption_ass.py, caption_srt.py, caption_ytt.py, word_timings.py)

### Takeaway
The caption pipeline is structurally compatible with Hindi (it splits on spaces, highlights whole space-separated words, writes UTF-8 and escapes safely), but it hard-codes a Latin-only font (Montserrat ExtraBold), measures line length in code points tuned for upper-case Latin, forces upper case, does not know the Devanagari danda (।), and its word timings depend on Parakeet transcription, which has no language setting and (inference) no Hindi support, so Hindi captions would fall back to character-count "estimated" timing.

### Cited Findings
- **Font named in the ASS style**: `FONT_NAME = "Montserrat ExtraBold"`, "The family name of the bundled font file (`assets/fonts/Montserrat-ExtraBold.ttf`)" — `backend/app/services/caption_plan.py:45-46`. It is used for the caption style (`caption_plan.py:143`, `:158`; written into the `Style:` line at `backend/app/services/caption_ass.py:139`), the source-line style (`caption_ass.py:106`) and the callout style (`backend/app/services/callout_render.py:54`, `:272`; `caption_ass.py:149`).
- A stored font name must match `[A-Za-z0-9 ]{1,60}` (`caption_plan.py:61`, checked at `:470`; same rule `callout_render.py:113`, `:971`). ASCII names such as "Noto Sans Devanagari" pass; this only constrains naming.
- **Upper-case transform**: the docstring says caption text is "upper case, with sentence punctuation removed" (`caption_plan.py:11-12`); `caption_text` ends with `" ".join(text.upper().split())` (`caption_plan.py:188`). Experiment E7 (local Python): `'हिन्दी GDP iPhone'.upper()` gives `'हिन्दी GDP IPHONE'` — a no-op on Devanagari, but English words inside Hindi text are capitalised.
- **Punctuation handling**: `caption_text` NFKC-normalises (`caption_plan.py:177`), turns em/en dashes into spaces (`:179`), strips quotes/brackets (`:180`), removes `.` and `,` except between digits (`:182`), removes `!?;:` (`:183`), keeps apostrophes only inside a word using `(?<!\w)['’]|['’](?!\w)` (`:185`), and trims hyphens (`:187`). The danda `।` (U+0964, category Po per E7) and double danda `॥` are in none of these sets, so they would stay glued to the last word of the burned caption.
- **Break after sentence punctuation**: `_SENTENCE_END = re.compile(r"[.,!?;:…—–]['\"”’)\]]*$")` (`caption_plan.py:62`, used at `:191-193`) — no danda, so a Hindi sentence end does not force a caption break (a pause of `PAUSE_BREAK_S = 0.30` s still does, `:54`, `:229`).
- **Line breaking / characters per line**: groups hold at most `MAX_WORDS = 4` words (`caption_plan.py:52`) and at most `max_chars` characters, `max_chars=14` in portrait (`:149`) and `28` in landscape (`:163`); length is `len(" ".join(word.text …))`, i.e. Unicode code points (`:239-240`); an over-long group is split at the word boundary that balances the two halves (`:243-254`), and "a single word is never split" (`:245`). The ASS header uses `WrapStyle: 0` (smart wrapping; `caption_ass.py:65`, `:168`), so libass may also wrap at spaces.
- **Font size / margins** are fractions of the frame height (portrait `font_size=round(height*0.042)`, `margin_v=round(height*0.28)`; landscape `0.065`, `0.09`) — `caption_plan.py:144-148`, `:159-162`. They were tuned for Montserrat.
- **Word-by-word highlighting**: one `Dialogue` event per word showing the whole group with that word wrapped in `{\c<highlight>}…{\c<normal>}`, words joined with a single space — `caption_ass.py:181-199` (join at `:197`). Highlighting is per space-separated word; nothing assumes Latin letters. Text is cleaned of `{ } \ CR LF` only (`caption_ass.py:66`, `:90-91`).
- **SRT**: uses the script's own casing and punctuation (`CaptionWord.raw`, `backend/app/services/caption_srt.py:5-7`, `:89-90`); `MAX_LINE_CHARS = 42`, `MAX_LINES = 2` in code points (`caption_srt.py:31-32`, `:96-112`); cue ends after `_SENTENCE_END = r"[.!?…]['\"”’)\]]*$"` (`caption_srt.py:39`) — no danda, so Hindi cues would only end at pauses, speech changes or the length/7 s limit (`:118-125`, `:143-146`). Written as UTF-8 (`caption_srt.py:164`; served at `backend/app/api/story_renders.py:516`).
- **YTT (SRV3)**: "Custom fonts are not possible, so the default font is used" (`backend/app/services/caption_ytt.py:12-13`); one `<p>` per word with segments joined by spaces and zero-width spaces (`caption_ytt.py:51`, `:121-147`); XML built with ElementTree, UTF-8 (`:23-24`, `:167-174`). No language attribute is written.
- **Word timings**: "The TTS provider returns no word times, so Parakeet transcribes the speech's WAV … and `align` matches the heard words back to the script's words" (`backend/app/services/word_timings.py:3-6`). The transcriber request has "no language field (Parakeet detects it)" (`backend/app/providers/transcriber.py:8-9`). Script words are `text.split()` (`word_timings.py:230`); tokens come from `dialogue_check.normalize_words` (NFKC, casefold, keep `isalnum()` or Unicode category M, everything else becomes a space — `backend/app/services/dialogue_check.py:172-184`), so Devanagari letters and vowel signs/virama are kept (E7: `ि`, `ी` are Mc, `्` is Mn). Below the match threshold the whole speech gets **estimated** timing "by character count" (`word_timings.py:28-31`, `:119-122`, `:250-256`); replaced spans are also shared out by `len(token)` (`:186-191`).
- ZWNJ/ZWJ (U+200C/U+200D) are category Cf (E7), so `normalize_words` turns them into spaces and splits the word into two tokens (`dialogue_check.py:181-184`).
- Captions are built for every explainer (`caption_plan.py:6-8`; `word_timings.py:276-280`) and SRT is the file uploaded to YouTube (`backend/app/jobs/publish_youtube.py:506`).

### Inferences
- With the current font, every Devanagari caption would render as empty boxes (proved for the same libass/font setup in Experiment E4, section 3).
- `max_chars` (14/28) is measured in code points calibrated for upper-case Montserrat ExtraBold. Experiment E6 (Pillow in the backend image): an English upper-case sentence in Montserrat ExtraBold measured 63.9 px per code point at 100 px, a Hindi sentence in Kohinoor Devanagari Regular 37.5 px per code point. Devanagari uses several code points per visible cluster (E7: `len("क्षेत्र") == 7`). So code-point limits would make Hindi groups shorter than the space allows. Switching `_length` to pixel width via `font_metrics.measure` would be script-neutral. Indicative only: a bold Devanagari display font would be wider than Kohinoor Regular.
- For Hindi audio under any architecture, Parakeet is the weak link: NVIDIA's published Parakeet TDT models are English (v2) or 25 European languages (v3), and Hindi is not among them (outside knowledge, not checked in this audit; the ASR researcher should confirm). If nothing matches, `align` falls back to estimated timing, and the word highlight would drift. Character-count estimation also over-weights words with many vowel signs and viramas. This makes Hindi caption timing an **L** item that depends on a Hindi-capable ASR or forced aligner.
- Word-level highlighting is compatible with Hindi because Hindi separates words with spaces and the `\c` override tags sit at word boundaries (Experiment E4C showed a coloured `५%` next to Devanagari words rendering correctly once a Devanagari font was named).
- For mixed Hindi + English captions, the upper-case rule should probably become "keep the script's casing" for Hindi projects (S), and the danda should be added to both sentence-end regexes and the punctuation strip list (S).

### Gaps
- Whether Breeze TTS 2 or the GPU server can return word timings for Hindi (which would remove the Parakeet dependency) was not checked; that is outside this rendering audit.
- YouTube's handling of a YTT file with Devanagari text (fonts, line-height in the player) was not tested.

## 2. Text measurement and fonts (font_metrics.py, bundled fonts, Pillow/RAQM, graphics_python, motion fonts and fitting, frontend fonts)

### Takeaway
Only two Latin fonts exist in the whole stack (Inter Medium and Montserrat ExtraBold). Neither has a single Devanagari glyph, and neither container has a system font that does. Every measurer (Pillow in Python, Canvas `measureText` in Chrome) and every drawer loads exactly those two families with no fallback list. Pillow does use the RAQM layout engine by default and shapes Devanagari correctly once given a Devanagari font. A dual-script font family (Devanagari + Latin) bundled in the same places as today is the core change, needed regardless of architecture.

### Cited Findings
- **Bundled fonts**: `backend/app/assets/fonts/` holds only `Inter-Medium.ttf` and `Montserrat-ExtraBold.ttf` (directory listing). `FONTS_DIR` and `FONT_FILE = … "Montserrat-ExtraBold.ttf"` — `backend/app/services/font_metrics.py:21-24`.
- **Experiment E2 (fc-scan in the backend image)**: Inter Medium's and Montserrat ExtraBold's fontconfig language lists include `en`, `ru`, `vi` and others but not `hi`, and their charsets contain no U+09xx (Devanagari) range. **Confirmed: neither font has Devanagari glyphs.**
- **Experiment E1 (backend image)**: the only system fonts are DejaVu (`fonts-dejavu-core 2.37-8`, pulled in by the `ffmpeg` package); `fc-list ":charset=0915"` (क) returns nothing; `fc-match "sans-serif:lang=hi"` and `fc-match "Montserrat ExtraBold"` both resolve to `DejaVuSans.ttf`, which has no Devanagari either. `backend/Dockerfile:7-9` installs only `ffmpeg`.
- **Experiment E3 (motion image)**: system fonts are only DejaVu (`fonts-dejavu-core 2.37-6`) plus `/app/public/fonts/{Inter-Medium,Montserrat-ExtraBold}.ttf`; no Noto font anywhere. `motion/Dockerfile:11-15` installs Chrome's libraries (`libpango`, `libcairo` …) and no font packages; `motion/Dockerfile:25` copies exactly the two font files.
- **font_metrics.py**: `measure(text, size)` uses Pillow `getlength` on the Montserrat file at 1000 px and converts to ASS size with Montserrat's own `usWinAscent (1109) + usWinDescent (453)`, which are "the font file's own numbers: change them with the file" — `font_metrics.py:31-45` (constant at `:35-38`).
- **Pillow version and layout engine (Experiment E1)**: Pillow 12.3.0 (`backend/uv.lock:972-973`, `backend/pyproject.toml:15`), `features.check("raqm") == True` (raqm 0.10.5), FriBiDi 1.0.16, HarfBuzz 14.2.1, FreeType 2.14.3. `ImageFont.truetype(...)` without `layout_engine` returns `layout_engine == 1` (RAQM) for both bundled fonts. No call site passes `layout_engine`, `language` or `features`: `font_metrics.py:33`, `backend/app/services/graphics_templates.py:183`, `backend/app/services/graphics_python/canvas.py:42`, `backend/app/services/thumbnail_compose.py:103` (Grep for `layout_engine|Layout\.|language=|features=` found none). `libraqm` is not installed by `backend/Dockerfile`; RAQM comes from the Pillow wheel, and the system `libfribidi0 1.0.16` it loads arrives as a dependency of `ffmpeg` (E1 dpkg list).
- **Experiment E5 (Pillow in the backend image)**: drawing "हिन्दी क्षेत्र कि" with the stand-in Devanagari font gives correct conjuncts and pre-base `ि` under RAQM, but broken output under `Layout.BASIC` (visible viramas, `ि` after the consonant); measured widths differ (RAQM 381.9 px vs BASIC 482.0 px at 80 px). Montserrat draws the same string as boxes (tofu). Image: `/tmp/visio_audit/pillow.png`.
- **Python templates (graphics_python)**: the two fonts per role are `FONT_FILES = {"display": "Montserrat-ExtraBold.ttf", "text": "Inter-Medium.ttf"}` (`graphics_templates.py:71-74`); `font_at(role, pixels)` loads one file (`canvas.py:39-42`); line boxes are `LINE_HEIGHT = 1.2 × size` (`graphics_templates.py:64-65`) with the baseline computed from that font's ascent/descent (`canvas.py:45-59`); `Canvas.text` draws one line with `anchor` `ls/ms/rs` and no language hint (`canvas.py:211-231`). `graphics_python/text.py:26-48` draws lines exactly as the spec laid them out ("nothing is fitted or broken here", `text.py:1-2`).
- **Text fitting in Python**: `graphics_templates.measure` (`:186-190`); `fit_text` tries one line, then every two-line split of `text.split()` words, shrinking to at most 70 % (`:193-221`, `MIN_SIZE_SHARE` `:62`); fields are refused above code-point limits (`line_of_text`, `:254-265`; `LIMIT_NAMES` `:166-174`; per-field limits in the catalogue strings, e.g. `"title": text (32)`, `"label": text (16)`, `:105`, `:118`, `:129`, `:144`, `:158`).
- **Motion (Remotion/Chrome) fonts**: `DISPLAY_FONT = "Montserrat ExtraBold"`, `TEXT_FONT = "Inter Medium"`, loaded with `@remotion/fonts` `loadFont` from `public/fonts` only, and "A missing font must fail the render, never fall back to another font silently" — `motion/src/fonts.ts:7-20`. `motion/scripts/copy-fonts.ts:10` copies exactly those two files for local work. The backend passes the same names (`backend/app/services/graphics_lab.py:79-84`, `FONTS`) into resolved briefs (`backend/app/services/graphics_resolve.py:364`, `backend/app/services/evidence_clips.py:187`, `backend/app/services/callout_graphics.py:296`).
- **Motion measurement**: `measureText` sets `canvas.font = \`${REFERENCE}px "${family(role)}"\`` — a single family, no fallback list — and caches widths (`motion/src/templates/layout.ts:118-129`); `family()` returns one of the two names (`layout.ts:64-66`); `LINE_HEIGHT = 1.2`, `FIT_SHARE = 0.97` (`layout.ts:9-10`). Drawn text uses `fontFamily: family(...)` with `whiteSpace: "nowrap"` per pre-split line (`motion/src/templates/Text.tsx:66-71`, `:134-136`; `motion/src/blocks/Item.tsx:48`).
- **motion/src/blocks/fit.ts**: words are `text.split(/\s+/)` (`fit.ts:77`), lines are re-joined with `" "` and the widest line minimised by dynamic programming (`fit.ts:35-63`); sizes come from `measureText` (`fit.ts:31-33`); "A text is never cut" (`fit.ts:3`).
- **Model-written components** must use `theme.fontDisplay` / `theme.fontText` "as `fontFamily`. Do not write a colour or font of your own." — `backend/app/services/graphics_component_writer.py:85-86`; the resolved fonts are passed in (`backend/app/services/callout_component_checks.py:76`).
- **Frontend fonts**: no `@font-face`, no custom font, no i18n library (Grep across `frontend/src` and `frontend/package.json` for `i18n|i18next|react-intl|lingui|formatjs|@font-face|font-family` found none beyond two inline styles: `frontend/src/components/settings/SettingRow.tsx:62` "serif", `frontend/src/components/imageLab/LabForm.tsx:215` monospace). Mantine is used with its default theme (`frontend/src/main.tsx:19`), whose font stack is `-apple-system, BlinkMacSystemFont, Segoe UI, Roboto, Helvetica, Arial, sans-serif, …` (`frontend/node_modules/@mantine/core/esm/core/MantineProvider/default-theme.mjs:5`). `frontend/index.html:2` has `<html lang="en">`.

### Inferences
- **Font choice for mixed Hindi + English.** Pillow and libass take one font per call or per style, and both showed tofu for Devanagari when the named font lacks it (E4, E5). So the simplest robust option is a single family that contains both Devanagari and Latin glyphs, in a display weight (for captions, callouts, titles, thumbnails) and a text weight, bundled in `backend/app/assets/fonts` and copied into motion as today. Candidate OFL families often cited as covering both scripts are Noto Sans Devanagari, Mukta, Hind and Poppins. This is outside knowledge that was **not verified** in this audit; glyph coverage and licences need checking. Alternatives are a Devanagari font paired with the current Latin fonts: CSS fallback lists in Chrome, script-run segmentation in Pillow, and a system-installed font for libass fallback. These are more complex.
- **Size of the font change: M, All.** The files that name fonts are `font_metrics.py:23-24`, `:35-38`; `graphics_templates.py:74`; `graphics_lab.py:79-84`; `caption_plan.py:46`; `thumbnail_compose.py:102-103`; `motion/src/fonts.ts:7-15`; `motion/scripts/copy-fonts.ts:10`; and `motion/Dockerfile:25`. Either per-project font selection (Hindi vs English projects) or one dual-script family for all projects; the latter is simpler but changes the look of existing English videos.
- **Vertical metrics, M, All.** Devanagari has vowel signs above the headline and below the base. With the stand-in font, ascent + descent at 100 px was 140 px versus Montserrat's 123 px (E6). `LINE_HEIGHT = 1.2` (Python and motion), the thumbnail's `_LINE_SPACING = 1.1` (`thumbnail_compose.py:45`), the ASS cell constant (`font_metrics.py:37`) and the caption margins will need re-tuning and visual checks, so upper/lower vowel signs are not clipped or overlapped between stacked lines.
- **Measurement is script-neutral once the font changes.** Pillow RAQM `getlength` and Chrome canvas `measureText` both shape text before measuring. So the measure-based fitters (`fit_text`, `fit.ts`, callout `_fit`, thumbnail `_layout`) should work for Hindi without logic changes. The exception is the code-point limits, covered in section 5.
- **Safety: S, All.** The silent downgrade from RAQM to BASIC would corrupt Devanagari (E5). It is only avoided because the image happens to have libfribidi via ffmpeg. An explicit `layout_engine=ImageFont.Layout.RAQM` plus a start-up check of `features.check("raqm")` would turn a silent corruption into a clear failure.
- Chrome shapes Devanagari with its built-in HarfBuzz, so the motion service needs only fonts, no engine change. This is established browser behaviour, not tested here. `measureText` and `fontFamily` must use the same family string (or the same fallback stack), or the layout will not match the drawing.
- **Frontend, S or none.** The story editor and panels will show Devanagari through operating-system font fallback (macOS ships Kohinoor Devanagari, seen locally; Windows ships Nirmala UI, outside knowledge). No font work is strictly needed in the UI. Setting `lang="hi"` on elements that show Hindi story text is optional polish.

### Gaps
- Which specific dual-script font family to adopt (glyph coverage, weights, licence, file size) was not evaluated.
- Chrome's rendering of Devanagari in the headless motion image was not tested (no Devanagari font is available there to test with).

## 3. FFmpeg and libass burn-in (backend/Dockerfile, ffmpeg.py, render_commands.py, render_story.py)

### Takeaway
FFmpeg 7.1.5 (Debian) with libass 0.17.3, HarfBuzz, FriBiDi and fontconfig is capable of Devanagari. But the render burns captions with the `subtitles` filter, which in this build drew Devanagari **unshaped** even with a Devanagari font named. The `ass` filter with `shaping=complex` drew it correctly. Also, libass did **not** fall back to a Devanagari font placed in the `fontsdir` folder when the style named Montserrat. So for Hindi the filter must change and the ASS styles must name a Devanagari-capable font. This is small, verified and needed under every architecture.

### Cited Findings
- `backend/Dockerfile:1` `FROM python:3.13-slim`; `:7-9` `apt-get install --no-install-recommends -y ffmpeg`.
- **Experiment E1**: `ffmpeg version 7.1.5-0+deb13u1`, configured with `--enable-libass --enable-libfontconfig --enable-libfreetype --enable-libfribidi --enable-libharfbuzz` (among others); `libass9 1:0.17.3-1+deb13u1`, `libharfbuzz0b 10.2.0`, `libfribidi0 1.0.16`, `fontconfig 2.15.0`. FFmpeg's verbose log reports `Shaper: FriBidi 1.0.16 (SIMPLE) HarfBuzz-ng 10.2.0 (COMPLEX)` and `Using font provider fontconfig`.
- **How fonts are passed**: `subtitles_filter` returns `subtitles=filename='<ass>':fontsdir='<fonts dir>'`, only for paths matching `[A-Za-z0-9/_.\-]+` — `backend/app/services/render_commands.py:795-809`; used as a separate `-vf` in `final_encode_args` (`render_commands.py:812-832`). The fonts folder is `font_metrics.FONTS_DIR` (`backend/app/jobs/render_story.py:99`, `:1845-1854`); the ASS file is written as UTF-8 (`render_story.py:1821-1824`). The docstring says the filter loads "the fonts of `fonts_dir` (and no other font file)" (`render_commands.py:799-800`).
- **No drawtext anywhere**: Grep for `drawtext|fontfile|force_style` across `backend/app` found no use; captions, callouts and source lines are all ASS (`caption_ass.py:1-7`, `:19-21`).
- **Experiment E4** (backend image, `ffmpeg -f lavfi color … -vf subtitles=…:fontsdir=…`, text "भारत की GDP ५% बढ़ी, हिन्दी क्षेत्र"):
  - A: style font Montserrat ExtraBold, fontsdir = bundled fonts → libass logs `Glyph 0x915 not found, selecting one more font for (Montserrat ExtraBold, 400, 0)` and draws every Devanagari character as a box; Latin "GDP" and "%" are fine (`/tmp/visio_audit/A_montserrat_onlybundled.png`).
  - B: the same, but with the Devanagari font also copied into `fontsdir` → **identical boxes**: libass did not fall back to the font in `fontsdir` (`/tmp/visio_audit/B_montserrat_with_kohinoor_in_dir.png`).
  - C: style font set to the Devanagari family → glyphs appear and Latin "GDP" renders in the same font, but conjuncts and the pre-base vowel sign are wrong (हिन्दी, क्षेत्र shown with explicit viramas) (`/tmp/visio_audit/C_kohinoor_named.png`).
- **Experiment E4b**: the same ASS file through `subtitles=…` (default), `ass=…:shaping=simple` and `ass=…:shaping=complex`: only `ass` with `shaping=complex` shapes हिन्दी / क्षेत्र / कि correctly (`/tmp/visio_audit/shaping_compare.png`). `ffmpeg -h filter=ass` lists `shaping` (auto/simple/complex, default auto); the `subtitles` filter rejected the `shaping` option ("Option not found").

### Inferences
- Required change (**S, All**): build the filter as `ass=filename='…':fontsdir='…':shaping=complex` instead of `subtitles=…` in `render_commands.py:809`, and name a Devanagari-capable family in the ASS styles (`caption_plan.py:46`, `callout_render.py:272`, `caption_ass.py:106`). Why `subtitles` ends up unshaped is not established. A plausible cause is that the filter forces libass's simple shaper because it has no `shaping` option. That is an inference; the observed behaviour is what matters.
- Mixed Hindi + English in libass needs either one family covering both scripts (E4C showed Latin rendering in the Devanagari family), or the Devanagari font installed system-wide in the backend image. With the second option, fontconfig fallback could find it while Montserrat keeps Latin. That fallback path is **untested**; E4B only shows that the `fontsdir`-only route fails.
- `font_metrics.measure` must use the same font file libass draws with (`font_metrics.py:1-10`), so callout fitting stays exact (`callout_render.py:31-36`).

### Gaps
- Whether `ass … shaping=auto` already selects complex shaping was not tested (only simple/complex were).
- Scene-level and AV-lab renders were not traced for other burn-in paths. Grep found only `render_story.write_subtitles` creating ASS files.

## 4. Thumbnails (thumbnail_compose.py, thumbnail_concept_writer.py, image prompt writers)

### Takeaway
The headline is drawn by code in Montserrat ExtraBold only, wrapped at spaces and limited to 40 code points / 6 words. The concept writer asks for the headline "in the language of the video", but nothing tells it what that language is. Image and video models are never asked to draw text, so no generative model has to render Devanagari.

### Cited Findings
- "The headline is drawn by code, not by the image model, so its spelling is always right" — `backend/app/services/thumbnail_compose.py:7-10`; font is always `font_metrics.FONT_FILE` (Montserrat ExtraBold) — `thumbnail_compose.py:102-103`.
- Wrapping splits on spaces and measures with `font.getlength` (`thumbnail_compose.py:106-121`); size steps down until ≤ `MAX_LINES = 2` lines fit (`:39`, `:124-143`); line spacing `_LINE_SPACING = 1.1` (`:45`); outline `stroke_width` 12 % of size (`:44`, `:133`); drawn with `canvas.text(..., stroke_width=outline, stroke_fill=_OUTLINE)` at the default anchor (`:191-198`).
- Concept writer: "Other programs draw the picture from your answer and write the headline on it. You never draw anything." ## 5. Graphics and callouts written by models (graphics_*_writer.py, callout_*_writer.py, shot_graphic_*_writer.py, checks, number display)

### Takeaway
On-screen graphic text is either written by code (numbers, in English/US formatting with `K/M/B/T`, `pts`, `x` and Latin "lakh/crore") or by models with code-point limits. Only the callout writer is told which language to use ("the language of the script"). The template, block and component writers that write titles and labels have no language rule. The "is this number said in the line" check understands digits (including Devanagari digits) and English number words only. In graphics briefs a mismatch is a hard refusal. There are no ASCII-only checks on text.

### Cited Findings
- **Callout writer**: "Write in the language of the script, in plain sentence case, with no emoji and no quotation marks." — `backend/app/services/callout_plan_writer.py:199-200`. Text limits per type in code points: emphasis 32, number 20, question 48, section title 32; list item 24; comparison side 24 (`callout_plan_writer.py:61-71`). Number callouts: `_number_warnings` — "Never a refusal" (`:408-418`).
- **Callout components**: "the model never writes a word: it shows the text of each part exactly as given" (`backend/app/services/callout_component_writer.py:12`).
- **Graphics brief writer**: "DO NOT write any text that appears on screen (titles, labels, captions). Other programs write it." (`backend/app/services/graphics_brief_writer.py:156-157`; same for shot graphics `backend/app/services/shot_graphic_brief_writer.py:207`). But facts carry a `label` (≤ 60, `graphics_brief_writer.py:66`) and are passed to the component as `facts: Record<string, { label; value; display }>` (`graphics_component_writer.py:56`). Units/scales are English words: `UNITS = ("usd", "inr", "percent", "points", "multiple", "count", "none")`, scales thousand/lakh/million/crore/billion (`graphics_brief_writer.py:43-52`; examples "12 billion dollars", "₹5 lakhs", "6.5 percent" at `:130-136`, `shot_graphic_brief_writer.py:185-191`).
- **Fact must be said in the line (refusal)**: `_check_said` locates `said_as` in the line and requires `numbers_in(...)` to read the value, otherwise `raise ValueError(... "A fact must be a number the line says.")` — `graphics_brief_writer.py:352-378` (rule stated at `:15-16`).
- **number_words.py**: "The numbers a text says, in digits or in English words" (`backend/app/services/number_words.py:1`); tokens are `\d[\d,]*(?:\.\d+)?(…k|mn|m|bn|b|cr)?|[a-z]+` on lower-cased text (`:80`, `:103-104`). Experiment E7: `Decimal('५०') == 50`, and the tokenizer on "भारत में ५० लाख लोग, 20 lakh, पाँच करोड़" yields only `['५०', '20', 'lakh']`. Devanagari digits are read, but Hindi number words (पाँच, लाख, करोड़) are invisible.
- **Template / block / component writers write on-screen text with no language rule**: "Texts (titles, labels, captions) are written by you, in plain words, and must be short" (`backend/app/services/graphics_template_spec_writer.py:52-56`); block scenes "Texts (titles, labels, cell texts) are written by you, in plain words" (`backend/app/services/graphics_block_scene_writer.py:77-88`); components "Texts that are not numbers are yours" (`graphics_component_writer.py:78-90`). Their example answers are English ("Hiring in spring", "March", "April": `graphics_template_spec_writer.py:61-63`; `graphics_block_scene_writer.py:111-113`).
- **Number text written by code** (`display_text`), "US style: `$` before dollars, `%`, `x` and ` pts` after percents, multiples and points; `K`, `M`, `B` and `T` for dollars and counts from 1,000 up … Rupees are Indian style: `₹` before them, and ` lakh` and ` crore`" — `backend/app/services/graphics_resolve.py:20-26`; constants `_PREFIX`, `_SUFFIX`, `K/M/B/T`, ` lakh`/` crore` at `graphics_resolve.py:85-99`; formatter `:195-221`.
- **Code checks**: no ASCII/Latin/Unicode checks in `graphics_code_checks.py` or `callout_component_checks.py` (Grep). The number-literal check `(?<![\w.$])\d[\d_]*…` (`backend/app/services/graphics_code_checks.py:66`, used `:192-196`, `:241-245`) also matches Devanagari digits, because Python `\d` is Unicode-aware.
- **Generic limit helper**: `text_limits.fit_text` accepts up to `max_chars × LIMIT_SLACK` code points, then cuts at a whole word (`backend/app/services/text_limits.py:56-69`).
- Python `\w` does not treat Devanagari vowel signs as word characters: E7 `re.findall(r'\w+', 'हिन्दी') == ['ह', 'न', 'द']`. In the audited text paths `\w` appears only in the apostrophe rule (`caption_plan.py:185`) and in code-safety regexes (`graphics_code_checks.py:43-66`), so there is no current breakage. This is a trap for future Hindi-aware code.

### Inferences
- **Under A (native Hindi)**: the callout writer will follow the script language automatically. The template, block and component writers will probably follow the script too, but nothing guarantees it, so an explicit target-language line is safer (**S**). The number check must learn Hindi number words: numerals 1–99 are irregular in Hindi, plus सौ, हज़ार, लाख, करोड़, दशमलव. Otherwise graphics briefs with Hindi-worded numbers will be **refused**: **M–L, A (and C if checks run against the Hindi script)**.
- **Under B (pivot)**: all these writers see English, so on-screen text comes out English and must be translated after layout-relevant decisions. The translated text must be re-fitted (refused or warned if too long) and re-checked by the browser layout checks. That adds a translation stage per text field: **M–L, B**.
- **Under C (hybrid)**: writers keep English reasoning but must emit Hindi display text. That means an explicit "on-screen text in Hindi" instruction in every text-writing prompt (callout plan, template spec, block scene, component, fact labels, thumbnail). The `said_as`/number checks need a decision: either Hindi number words are supported, or the checks run on an English shadow of the line. **M, C**.
- **Number display (All, M)**: `display_text` produces `12K`, `3.5M`, `+158%`, `6x`, `5 pts` and `₹5 lakh`. For Hindi on-screen text, at least the scale words (`लाख`, `करोड़`, and for USD probably `हज़ार/लाख/करोड़` or Latin `K/M/B`) and the digit style need product decisions. Most Hindi news graphics use international (Latin) digits, which would keep `0-9` (outside knowledge; flag).
- **Limits (All, S–M)**: the code-point limits (callout 20–48, template fields 10–48, fact labels 60) are calibrated for English. With the measure-based fitting downstream they could be raised for Hindi or replaced by width checks.
- **Mixed Hindi + English (All)**: brand names and acronyms in Latin inside Hindi labels need the dual-script font (section 2). Callout and graphics measurement already measures whole strings, so no segmentation is needed if one font covers both.

### Gaps
- Whether the current LLM writes good Hindi within these code-point budgets was not assessed (prompt-quality question for another researcher).
- The browser layout checks in `graphics_blocks.py` (`layout_problems`, `callout_layout_problems`) were not read in depth. They measure in the browser and should inherit the font fix, but minimum-text-height rules were not reviewed for Devanagari.

## 6. Evidence (evidence_text.py, evidence_source_lines.py, evidence_layout.py, evidence_clip_layout.py, evidence-capture text.py)

### Takeaway
Quote matching is exact substring matching after a Unicode-aware normalisation (NFKC, quote folding, removal of soft hyphen/ZWSP/ZWNJ/ZWJ, whitespace collapsing, case kept). It should work for Hindi web pages whose text is proper Unicode, but Hindi PDFs are a risk. What the evidence layer *draws* in its own text is English: "Source: …", English month abbreviations and "p. N", in Montserrat/Inter. The capture browser runs with `locale: en-US`, and the research brief always says `"language": "en"`.

### Cited Findings
- **Normalisation contract (copied in two places)**: NFKC applied to "a letter and the marks after it together"; curly quotes to straight; "soft hyphens and zero-width characters are removed"; whitespace collapsed; "letter case is kept"; PDF hyphen handling in three modes — `backend/app/services/evidence_text.py:1-19`, `tools/evidence-capture/src/visio_evidence_capture/text.py:1-15`. Removed set `"\u00ad\u200b\u200c\u200d\u2060\ufeff"` (`evidence_text.py:46`; `text.py:40`). Grouping uses `unicodedata.combining(...)` (`evidence_text.py:96-100`; `text.py:90-94`). Matching is `wanted in normalise_with_map(text).text` (`evidence_text.py:119-130`) / `source.text.find(quote)` (`text.py:132-145`). `nearest_text` uses `casefold()` and whitespace word splitting (`text.py:148-196`).
- E7: Devanagari vowel signs `ि`/`ी` have combining class 0, virama 9 — so most vowel signs are not grouped with their consonant, and each is normalised as its own piece. NFKC decomposes composition-excluded nukta letters (क़ U+0958 → U+0915 U+093C).
- **Quote length** is checked in code points after normalisation (`QUOTE_MIN_CHARS`/`QUOTE_MAX_CHARS`) — `tools/evidence-capture/src/visio_evidence_capture/web.py:242-252`.
- **Capture browser locale**: `"locale": "en-US"` in the Playwright context — `web.py:428`. Web text is read via `innerText` (`web.py:98`). PDFs are read with pypdfium2 `get_text_range()` (`evidence_text.py:147-155`).
- **Research brief language**: `"language": "en"` in `brief/claims.json` — `backend/app/services/evidence_rounds.py:217`; the agent skill describes `project.language` as "for your information" (`~/.claude/skills/visio-evidence/SKILL.md:31`, outside the repository).
- **Text the evidence layer draws itself**: badge publisher falls back to the host name and then to the literal `"Source"` (`backend/app/services/evidence_clips.py:138-155`, literal at `:153`); dates formatted as `3 Oct 2026` with English month abbreviations (`evidence_clips.py:92-105`, `:127-135`); source line text `"Source: " + publisher, date` (`evidence_clips.py:770-774`), drawn by libass in the `SourceLine` style with `FONT_NAME` (Montserrat) and cut to 90 code points (`caption_ass.py:53-57`, `:103-125`, slice at `:117`); badge text in Remotion uses `resolved.fonts.display` / `.text` (`motion/src/evidence/Evidence.tsx:170`, `:182`) and the page label `p. ${page}` (`Evidence.tsx:102`). Publisher/date are cleaned and cut by code point: `text[:limit]` (`evidence_clips.py:117-123`).
- `evidence_source_lines.py` only decides *when* a source line shows (`backend/app/services/evidence_source_lines.py:50-82`). `evidence_layout.py` and `evidence_clip_layout.py` are geometry only: split panels, badge strip, zoom to quote rectangles (`backend/app/services/evidence_layout.py:1-22`; `backend/app/services/evidence_clip_layout.py:9-16`, `:180-197`). The quote itself is shown as a screenshot (pixels) captured by the tool.

### Inferences
- **Hindi web sources** (A/C, M for testing): matching should work because both the quote and the page text pass through the same normalisation, and DOM text is in logical Unicode order. Removing ZWNJ/ZWJ is harmless for matching (both sides) and avoids mismatches caused by optional joiners. Per-piece NFKC is consistent on both sides. Not tested with real Hindi pages.
- **Hindi PDFs** (A/C, M–L): many Indian government and newspaper PDFs use legacy non-Unicode fonts (e.g. Kruti Dev) or lack proper ToUnicode maps. Text extraction can then return glyph-order text, with the short-i vowel sign before its consonant, or Latin garbage, and exact matching fails. This is outside knowledge about PDFs, **not verified** with pypdfium2 here.
- **locale en-US** affects `Accept-Language` and `navigator.language`, so bilingual sites may serve English pages. For Hindi sources the capture should use `hi-IN` (or a per-round locale): **S, A/C**. The brief's `"language": "en"` should come from the project language: **S**.
- **Badge and source line** (All, S): localise `"Source"`, the month names (or use numeric dates) and `p.`, and use the Devanagari-capable font in the `SourceLine` ASS style and the badge. Cut by grapheme cluster, not code point (`caption_ass.py:117`, `evidence_clips.py:123`), so a cut never leaves a dangling virama or vowel sign (E7: `'क्षेत्र'[:2] == 'क्'`).
- **Mixed-language evidence**: under B/C an English-language source screenshot inside a Hindi video is plausible. Nothing technical blocks it. It is an editorial choice.
- The capture tool itself draws only highlight boxes, not text (`tools/evidence-capture/src/visio_evidence_capture/draw.py`, 72 lines, no `ImageFont` per Grep). The fonts on the capture machine (the owner's Mac has Devanagari fonts) decide how Hindi pages look in screenshots.

### Gaps
- No real Hindi web page or PDF was put through the capture/import matching.

## 7. Publishing (youtube_draft_writer.py, youtube_draft.py, youtube_publish.py, youtube_api.py, frontend youtubeLimits.ts)

### Takeaway

(`youtube_api.py:60`).
- No `localizations` / `localized` anywhere in the backend (Grep returned nothing).
- Draft writer rules end with "Write in English." (`backend/app/services/youtube_draft_writer.py:65-69`); the example answer is English (`:112-116`).

### Inferences
- **Language codes (S, All)**: set `defaultLanguage` / `defaultAudioLanguage` to `hi` for Hindi projects, and upload the caption track as `hi` with a Hindi name, from a project language value. Under B/C a second, English caption track and `snippet.localizations` (an English title and description) could be added, which needs `defaultLanguage` set (outside knowledge about the YouTube Data API; verify): **M** if bilingual metadata is wanted.

It must allow Unicode letters and marks (e.g. `[\p{L}\p{M}\p{N}_]+` in the frontend; in Python, the `regex` module or an explicit category check). Lower-casing is harmless for Devanagari.
- **Draft language (S; architecture-dependent)**: replace "Write in English." with the project language. Under B, a translation of the English draft is the alternative.
- **Byte budget (S, All)**: 1500 Devanagari characters is about 4500 bytes, so with hashtags a Hindi description aimed at the current target could approach the 5000-byte limit. The aim should be in bytes or lower for Hindi. Whether YouTube's 100-character title limit counts code points or grapheme clusters for Devanagari is unknown, so the code-point count is the conservative choice.

## 9. Frontend handling of story text (storyLength.ts, slugFromName.ts, storyMarks.ts, editorParts.tsx, voice/accent fields, font stack)

### Takeaway
The frontend has no i18n and that is fine for this question. The code that processes story text is mostly script-neutral: whitespace word counts, code-point positions. Devanagari will display through the OS font fallback in the Mantine system font stack.

### Cited Findings

- `storyMarks.ts` converts between code points (as the backend counts) and UTF-16 units; it does not segment words (`frontend/src/components/story/storyMarks.ts:1-28`). `editorParts.tsx` is generic list-input UI with no text processing (`frontend/src/components/story/editorParts.tsx:1-30`).
- Accent fields: the character view lists "Accent" (`frontend/src/components/characterLab/CharacterDefinitionView.tsx:78`); the backend accent is free text ≤ 80 chars with the example "soft regional accent" (`backend/app/services/character_definition_writer.py:60`, `:117`). - Font stack: Mantine default system stack (`default-theme.mjs:5`), `<html lang="en">` (`frontend/index.html:2`).

### Inferences
- Word counts work for Hindi (words are space-separated), but the default words-per-minute value is presumably tuned for English narration. Hindi narration pace differs, so the length estimate needs a per-language value: **S, All**.
- `slugFromName` gives `item`, `item_2`, … for Devanagari names. It is cosmetic, since the user can edit the id, but a transliteration or a fallback based on the row number would be nicer: **S, optional**.
- Accent and voice descriptions in English are internal prompts to the voice-design model. That is acceptable under all three architectures; the accent value for Hindi voices is a TTS question for another researcher.

### Gaps

### Inferences
- **Needed regardless of architecture**: items 1–14 and 17, 20–24. The rendering core is 1, 2, 3, 4, 9, 10 and 11, roughly M overall. Caption timing (12) is the only L item here, and it depends on ASR capability rather than rendering code.
- **Mixed Hindi + English text**: it works without script segmentation if one font covers both scripts (E4C rendered "GDP" and "%" correctly inside Devanagari text with a Devanagari family named). The remaining mixed-text decisions are the upper-case rule (item 8), digit style (item 14), hashtags in both scripts (item 21), and ASR that handles code-mixed speech (item 12).
- **Architecture-specific work** concentrates in items 15, 16 and 18–19. A gets script-following behaviour almost free but needs Hindi number words and Hindi evidence. B needs a translation and re-fit stage for every displayed text field. C needs explicit Hindi-output instructions in every text-writing prompt and a decision on where the "number is said" checks run.

### Gaps
- None of the font, metrics or shaping fixes was tested end to end in an actual render (experiments only rendered single frames). Final font choice and visual tuning remain open.
- Adjacent areas deliberately left to other researchers: TTS (Breeze TTS 2) Hindi support and its chunking (`speech_chunks.py`), ASR for Hindi, LLM Hindi writing quality, and voice/accent design.
